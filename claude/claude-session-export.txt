  How it's built
  - Re-runnable: each table is created only if it doesn't already exist, then
    loaded with MERGE. A row is updated only when a fingerprint of its contents
    changes, so running it twice on the same raw data changes nothing.
  - Light cleaning only: IDs are trimmed and empty strings become NULL.
    session_type and style are lowercased, and a missing is_deleted is treated
    as FALSE. Deleted and incomplete records are kept, so later models can still
    look at the data as it stood at any point.
  - Duplicates: each table is cut down to one row per key in a fixed order, so
    the same row wins every run. A _source_row_count column shows how many raw
    rows were merged, so duplicates in raw stay visible.
  - Load tracking: _first_loaded_at and _last_updated_at record when each row
    arrived and last changed. If a row disappears from raw, the three smaller
    tables set _removed_from_source_at rather than deleting it.
  - Primary keys: declared as NOT ENFORCED. BigQuery uses them to plan joins,
    and they map directly onto a production application database.

  stg_responses (built for the 100m+ rows)
  - Split into daily partitions on answered_at and clustered by pupil_id,
    session_id, question_id.
  - Loaded incrementally: each run reprocesses from the latest staged
    answered_at minus a 3-day lookback, to catch late-arriving rows. The MERGE
    only scans the target partitions in that window. Set full_refresh = TRUE at
    the top to reprocess everything.
  - The other three tables are small, so they're fully merged every run.
    stg_assessment_sittings is partitioned by month on started_at.

  Assumptions to check against your profiling
  1. Sittings key: I used (pupil_id, session_id), because your join matches on
     both columns. If session_id is unique on its own, the key can be
     simplified.
  2. Pupils and course hierarchy have no timestamps, so there's no way to tell
     which duplicate is the latest:
     - A pupil counts as deleted if any of their raw rows says so.
     - If a question appears more than once, one row is kept by a fixed rule and
       _source_row_count > 1 flags it.
  3. History: the course hierarchy is a current snapshot with no validity dates.
     To score a pupil as of a past date when a question has since moved
     subject, you'll need a snapshot table built on top of staging. Responses
     don't have this problem because answered_at timestamps each event.
  4. Lookback window: a response that turns up in raw more than 3 days after the
     latest staged answer would be missed by the incremental load. Increase
     responses_lookback_days if your data arrives later than that.
  5. Raw table cost: if de_raw.responses isn't partitioned itself, the
     incremental read still scans the whole raw table. That's worth raising with
     whoever owns de_raw.

❯ If a row changes in the source, it looks like the row is overwritten in       
  staging along with _last_updated_at. Does this mean that point in time        
  analysis will not be possible?                                                

⏺ Yes. As written, each staging table holds only the current state: when a
  source row changes, the old values are overwritten and lost. How much that
  matters depends on the table.

  Table: stg_responses
  Point-in-time today: Mostly works: filter on answered_at <= T
  What's lost when a row changes: A corrected response (for example is_correct
    flipped, or a re-mark) overwrites the original, so a score recomputed for an

    earlier date uses the new value.
  ────────────────────────────────────────
  Table: stg_assessment_sittings
  Point-in-time today: Breaks
  What's lost when a row changes: Changes to is_deleted, is_complete,
  finished_at
    and total_questions. You can't tell whether a sitting counted as of a past
    date.
  ────────────────────────────────────────
  Table: stg_course_hierarchy
  Point-in-time today: Breaks
  What's lost when a row changes: A question moving subject or topic. Old scores

    silently move to the new subject.
  ────────────────────────────────────────
  Table: stg_pupils
  Point-in-time today: Breaks
  What's lost when a row changes: When a pupil was deleted. A pupil deleted
  today
    disappears from past results too.

  _last_updated_at only tells you that a row changed, not what it was before.

  Recommended fix: keep every version, and put a current-state view on top

  Make each staging table insert-only, adding a new version only when a row's
  fingerprint differs from its current version:

  stg_<entity>_history
    <natural key>, <business columns>,
    _row_hash,
    _valid_from      TIMESTAMP NOT NULL   -- run_ts when this version was first 
  seen
    _valid_to        TIMESTAMP            -- NULL = current version
    _is_current      BOOL
    _is_deleted_in_source BOOL            -- a hard delete becomes its own 
  version
    PRIMARY KEY (<natural key>, _valid_from) NOT ENFORCED

  - Point-in-time query: WHERE _valid_from <= T AND (_valid_to > T OR _valid_to 
    IS NULL).
  - Current state: a stg_<entity> view filtered on _is_current. That way a
    colleague extending it next month doesn't need to know about the history.
  - Re-runnable: a second run with unchanged source data inserts nothing and
    closes nothing, so it stays a no-op.
  - Responses at volume: changed versions should be rare, so the history table
    stays roughly the size of the current one. Keep partitioning on answered_at
    so the incremental load still only scans recent partitions.

  Limits of this fix:
  1. History starts at the first load. The raw tables have no update timestamps,
     so anything that changed before we start capturing can't be recovered.
  2. "As it stood" means "as known when our job ran". _valid_from is when our
     job saw the change, not when it happened in the app. A change made at 09:00
     and loaded at 23:00 shows as 23:00. For true event time, the source needs
     an updated_at or change-data-capture feed into de_raw, which is worth
     asking for.
  3. A full rebuild can't reproduce history. You can't regenerate history from
     the current raw tables, so these history tables must never be dropped and
     rebuilt. That should be documented, and the tables should ideally be
     protected.

  How a load works
  1. Raw is cleaned and deduplicated into a temp table, exactly as before.
  2. It's compared with the current versions. Rows that are new, changed, or
     back after being removed get a new version. Keys missing from raw get a
     "tombstone" version that keeps their last known values and is marked as
     deleted from source.
  3. The old versions are closed and the new ones inserted inside one
     transaction, so readers never see a key with no current version or two.

  Re-runnable: running again on unchanged raw data writes nothing. Each file
  also checks that the run time is later than the latest version already stored,
  so versions can't be written out of order.

  Responses
  - It still loads incrementally, reading raw from the latest staged answer
    minus 3 days; full_refresh reads all of raw.
  - Changes are compared against all current versions, not just the 3-day
    window. That stops a response whose answered_at moved from ending up with
    two current versions. The cost is reading three narrow columns of the
    history table each run, which is small compared with reading whole rows.
  - Hard deletes are only detected inside the window (or across everything on a
    full refresh).
  - A point-in-time score usually combines two filters:
    - answered_at <= T: what had been answered by then.
    - stg_responses_as_of(T): the values as we knew them then.

  Things to know before running
  - Old tables block the views. If you ran the earlier version, tables called
    stg_pupils, stg_responses and so on already exist, and creating the views
    will fail. Drop those four tables first; I haven't added that to the scripts
    because it deletes data.
  - "As of" means load time. History starts at the first run and records when
    our job saw each change, not when it happened in the app. True event time
    needs an updated_at or change feed in de_raw.
  - Never drop or rebuild the _history tables. The history can't be regenerated
    from raw. Each table's description says so, and they should ideally be
    protected from deletion.

❯ Each time these files are re-run the view and the point in time function get  
  recreated. Is this an unnecessary step when just running an update?           

⏺ It isn't harmful, but on a routine load it's unnecessary, and it's better
  moved out.

  Why it does no harm
  - Recreating a view or table function only changes metadata. It costs nothing,
    takes about a second, scans no data, and gives the same result every run.
  - Queries already running against the view aren't affected.

  Why it's still worth moving out
  - Permissions: the scheduled load job needs rights to create views and
    functions. A load job should ideally only need to read de_raw and write the
    history tables.
  - Mixed responsibilities: structure changes become part of every data load.
    When a colleague changes a view next month, it goes live on the next
    scheduled run rather than as a deliberate deployment.
  - Silent reverts: if someone hot-fixes a view in the console, the next load
    quietly puts the old definition back.
  - Audit noise: every run logs view and function changes, which makes real
    structure changes harder to spot.

  Why not just switch to CREATE VIEW IF NOT EXISTS?
  It would stop the recreation, but then a change to a view's definition would
  never be applied anywhere it already exists. That swaps an unnecessary step
  for a deployment bug.

  Recommendation: split each table into deploy and load files

  rebecca_fleming_staging/
    ddl/                         -- run on deploy, when structure changes
      00_create_dataset.sql
      stg_pupils.sql             -- history table (IF NOT EXISTS), view, as-of 
  function (OR REPLACE)
      ...
    load/                        -- run on every schedule
      stg_pupils.sql             -- check, temp tables, transaction only
      ...

  - ddl/ keeps CREATE OR REPLACE for the views and functions, so a definition
    change is applied in every environment when you deploy. History tables stay
    IF NOT EXISTS, so a deploy can never wipe history.
  - load/ contains only the load steps: the run-time check, the temp tables and
    the transaction. The scheduled job can then run with read access to de_raw
    and write access to the _history tables only.
  - The cost: a brand-new environment needs ddl/ run before load/. That's the
    normal ordering in any deployment pipeline.

⏺ I've built the SATs score model on top of staging, in a new folder
  /home/user/rebecca_fleming_sats/ with the same ddl/ and load/ split and a
  README giving the run order. None of it has been run against BigQuery, because
  my login still fails, so I haven't seen your subject names or checked any
  scores. Every file passes a syntax check, though the checker can't read ASSERT
  statements or table functions, so those parts were only checked in simplified
  form. The check caught one real bug, which I fixed.

  Converting a percentage to the 80–120 scale
  - I used the official GOV.UK conversion tables for 2024, 2025 and 2026 for
    maths, reading and GPS (grammar, punctuation and spelling), stored with a
    link to the source page on every row.
  - A pupil's percentage becomes an equivalent KS2 mark: FLOOR(correct × max 
    mark ÷ questions presented). Maths is out of 110, reading 50 and GPS 70. The
    scaled score is then read from that year's table.
  - The year's table is chosen by the academic year of the sitting. Sittings
    this academic year (2026/27) use the 2026 table until a 2027 one is added.
  - GOV.UK gives no scaled score below 3 marks. Because you asked for 80–120,
    those are set to 80 and flagged is_below_scaled_range.

  What gets built
  - fct_sats_score_history: one score per pupil, subject and sitting, with the
    period each score was in effect (from that sitting until the pupil's next
    one in that subject). This is the table to migrate to the app database: one
    stable ID column, plain types that map directly to Postgres, nothing nested.
  - pupil_subject_sats_score: a view of every current pupil against every
    subject, with the latest score or no_assessment if they've never been
    assessed.
  - Point in time, two ways:
    - pupil_subject_sats_score_as_of(T) gives the score in effect on date T,
      using everything we know now.
    - int_sats_sitting_scores_as_of(T) recomputes what the model would have
      reported on date T, ignoring corrections loaded since. The scoring logic
      lives only in this one function, so both views stay consistent.
  - Re-runnable: rows are rewritten only when their content changes, so a second
    run with the same inputs changes nothing in the score table.
  - Incremental: each run recomputes only pupils whose staging data changed
    since the last run, plus a 24-hour overlap for late loads. Changing the
    conversion tables or the subject mapping triggers a full recompute
    automatically.

  Decisions you should check
  1. Current score comes from the latest sitting in that subject, not an average
     over all sittings. A short assessment will give a noisy score;
     questions_presented is stored so you can set a minimum.
  2. Percentage = correct ÷ answer rows recorded. A no-attempt counts as wrong.
     A question in the sitting with no answer row at all isn't counted, which
     would inflate the percentage if the app doesn't log skipped questions.
  3. Subject mapping is guessed from subject names, because I couldn't see your
     data. Names containing "math" use maths, "grammar" or "spelling" use GPS,
     and "reading" uses reading. Anything else (for example "Science") is scored
     on the average of the three curves. Check ref_subject_ks2_mapping after
     the first load; any row you correct and mark manual is never overwritten.
  4. Which sittings count: complete, not deleted, from pupils who aren't
     deleted. If session_type or style marks practice sessions that shouldn't
     count, a filter needs adding in the sittings step of the scoring function.

⏺ I've added int_pupil_subject_session_summary: one row per pupil, subject and
  session, covering every subject and every sitting. The SATs scores are now
  built on top of it. All files pass the syntax check, but nothing has been run
  in BigQuery.

  What the summary holds
  - No filtering: incomplete sittings, deleted sittings and deleted pupils are
    all kept, with flags (sitting_is_complete, sitting_is_deleted,
    pupil_is_deleted), so each future query chooses its own rules.
  - Question counts: presented, correct, incorrect and not attempted, which
    always add up to presented. It also counts answers replaced by a later
    answer to the same question.
  - Percentages: percent correct, and percent correct out of attempted questions
    only.
  - Coverage: number of distinct topics, subtopics and atoms answered.
  - Timing: total seconds, average seconds per question, and first and last
    answer times.
  - Sitting details: assessment, session type, style, year group, academic year,
    started and finished times.
  - Key: summary_id is the same value as fct_sats_score_history.sats_score_id,
    so a SATs score joins one-to-one to its summary row.
  - Point in time: int_pupil_subject_session_summary_as_of(T) recomputes the
    summary as it was known on date T.

  How the SATs model changed
  - The SATs scoring function now reads the summary and only applies the SATs
    rules on top: which sittings count, English and Maths only, and the GOV.UK
    conversion. Answers are no longer counted in two places.

  Shared pieces, for whoever extends this next
  - int_changed_pupils(since): returns pupils whose staging data changed after a
    given time. The summary load and the SATs load both use it, and any new
    pupil-level model can too.
  - model_run_log: replaces the SATs-only run log, with one row per load of each
    model, so each table tracks its own last run.
  - Automatic full refresh: each load now also recomputes everyone when the
    definition of any function it depends on changes, checked through BigQuery's
    list of function definitions. The SATs load also does this when the
    conversion tables or subject mapping change, as before. Without this,
    editing a function would leave old rows computed the old way.

  Two things to know
  - Excluded rows: responses that don't belong to a sitting, or whose question
    has no subject in the hierarchy, aren't in the summary, because subject is
    part of the key.
  - Answers counted twice per run: the SATs load computes from the summary
    function, not the stored summary table. That keeps the scoring logic in one
    place and allows recompute for any date. The cost is that changed pupils'
    answers are counted again in each load, which should be small because only
    changed pupils are recomputed. The README notes how to switch if it becomes
    expensive.
